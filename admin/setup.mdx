# AutoSurvey Setup Home

This guide explains every item on the **AutoSurvey Setup Home** page: what it checks, why it matters, and how to fix issues quickly.

## Quick Start

After installing AutoSurvey, open the **AutoSurvey** app and click the **Setup** tab.

The Setup Home page runs automated checks and shows what is ready versus what still needs attention. Most issues can be repaired with a single button click.

## Required Checks

All required checks must pass before AutoSurvey can function correctly.

If a required check fails:
- The progress indicator reflects it.
- A repair action appears.

### Admin Access

| Item | Details |
| --- | --- |
| **What it checks** | Whether the current user has the `ASVY_Full_Admin` permission set group (preferred) or all three admin permission sets: `AutoSurvey_Admin`, `ASVY_Deploy_Admin`, and `AutoSurvey_Survey_Admin`. |
| **Why it matters** | Without admin permissions, you cannot configure surveys, deploy flows, or manage suite settings. |
| **How to fix** | Click **Assign Admin Access to Me**. AutoSurvey assigns `ASVY_Full_Admin` when available; otherwise it falls back to assigning required individual permission sets. |
| **Troubleshooting** | If assignment fails, a System Administrator can manually assign permission sets in **Setup -> Permission Sets**. |

### Internal Connection

| Item | Details |
| --- | --- |
| **What it checks** | Whether the `AutoSurvey_Self_Org` Named Credential exists and points to your current org domain. |
| **Why it matters** | AutoSurvey uses this connection for internal API and metadata operations (including flow deployment). |
| **How to fix** | Click **Repair Internal Connection** to create or update the Named Credential to your current org URL. |
| **After sandbox refresh** | This is the most common check to fail after refresh because org domain URLs change. |
| **Technical detail** | AutoSurvey uses `ConnectApi.NamedCredentials` with current `URL.getOrgDomainUrl()` and `AutoSurvey_Self_Org` external credential access. |

### Control Plane Connection

This check appears in subscriber orgs (most customers). In control plane orgs, the same slot appears as **Google Credentials** instead — see the next section.

| Item | Details |
| --- | --- |
| **What it checks** | Whether your org is connected to the AutoSurvey control plane (secure intermediary for Google API operations). |
| **Why it matters** | AutoSurvey needs Google Sheets and Drive access for survey definitions and suite sheet operations. |
| **How to fix** | Click **Connect to Control Plane** for one-time bootstrap registration. |
| **Troubleshooting** | Verify outbound HTTPS callouts are allowed and check the `AutoSurvey_Control_Plane` Named Credential configuration. |
| **Technical detail** | Bootstrap generates/stores HMAC keys (`ASVY_Bootstrap_Secret__c`) and registers org identity for signed control-plane requests. |

### Google Credentials

This check appears in control plane orgs (the AutoSurvey hosting/dev org), which call Google APIs directly instead of routing through the control plane.

| Item | Details |
| --- | --- |
| **What it checks** | Whether `Autosurvey_Salesforce_Bot_Google` external credential and Google Named Credentials are configured. |
| **Why it matters** | The control plane org connects directly to Google APIs through service-account-backed credentials. |
| **How to fix** | Click **Deploy Google Credentials** to create credentials and required permission set. |

### Google Sheets Access

This check appears in control plane orgs only.

| Item | Details |
| --- | --- |
| **What it checks** | Whether the current user has `Autosurvey_Salesforce_Bot_Google_Access`. |
| **Why it matters** | Users making Google API callouts need principal access to the external credential. |
| **How to fix** | Click **Fix Google Access** to assign the permission set to your user. |
| **Note** | Subscriber orgs do not need this because Google calls route through the control plane. |

### Connection Verification

| Item | Details |
| --- | --- |
| **What it checks** | Live connectivity test to Google APIs (direct or via control plane). |
| **Why it matters** | Verifies end-to-end runtime path, not just static configuration. |
| **How to fix** | Click **Test Connection** (or **Re-verify**). |
| **Status values** | **Pass** = successful API response. **Fail** = request returned error. **Not Tested** = no verification run yet. |
| **Troubleshooting** | Ensure prior checks pass, inspect detail error message/status code, and contact support if control plane errors persist. |

### Response Owner Queue

Shown on Setup Home as **Guest Response Queue**.

| Item | Details |
| --- | --- |
| **What it checks** | Whether the `AutoSurvey_Response_Owners` queue exists and can own every guest-written survey object. |
| **Why it matters** | Public (guest / Experience Cloud) survey responses are owned by this queue so anonymous visitors cannot read each other's data. Queues cannot ship inside a managed package, so it is created at setup time. Without it, guest survey saves fail. |
| **How to fix** | Click **Create Response Owner Queue**. The action is idempotent — safe to re-run, and it also repairs a queue that exists but is missing objects. |
| **Status values** | **Pass** = queue exists and owns all guest survey objects. **Fail** = queue is missing, or exists but cannot own some objects (the detail lists which). |

## Permission Sets

Setup Home shows installed AutoSurvey permission sets, assignment counts, and assignment details.

| Permission Set | Purpose |
| --- | --- |
| **AutoSurvey_Admin** | Core admin access to AutoSurvey objects and settings. |
| **ASVY_Deploy_Admin** | Deployment/schema permissions, including `ASVY_Deploy` custom permission. |
| **AutoSurvey_Survey_Admin** | Runtime survey administration and management access. |
| **ASVY_Super_User** | Elevated troubleshooting and diagnostic access. |
| **ASVY_Self_Org_Access** | Access to `AutoSurvey_Self_Org` Named Credential for self-org callouts. |
| **AutoSurvey_Guest_Access** | Minimum access for Experience Cloud guest users taking surveys. |

> Tip: For most admins, assign **ASVY_Full_Admin** (permission set group) instead of individual sets.

## Prepare for Uninstall

The **Uninstall Preparation** card readies the org for uninstalling the AutoSurvey package. Clicking **Prepare for Uninstall** removes every removable AutoSurvey permission set and permission set group assignment for **all users in the org**, then scans for uninstall blockers it cannot clear for you (such as a custom object of yours with a relationship field pointing at an AutoSurvey object) and lists them with instructions.

<Warning>
This action is destructive and org-wide: it revokes AutoSurvey access for every user, not just you. And uninstalling the package afterward permanently deletes all survey response data stored in the package's objects. Export responses first — the card shows how many submissions are affected and requires you to acknowledge the export before the button enables.
</Warning>

The result reports what was removed, any profile-owned assignments Salesforce requires you to clear manually, and remaining blockers to clear by hand before the uninstall will run. **Ready** means no known blockers remain — a scan, not a guarantee: an unpublished Experience Builder draft or a deleted-but-not-erased custom object can still block the uninstall without being visible to any check.

## Control Plane Security

This section appears for subscriber orgs after control plane connection succeeds.

### HMAC Key Rotation

| Item | Details |
| --- | --- |
| **What it does** | Rotates the HMAC key used for org-to-control-plane request signing. |
| **When to rotate** | Periodically (for example quarterly) or immediately if key compromise is suspected. |
| **Grace period** | Previous key remains valid for 7 days to avoid service interruption. |
| **Key ID** | Setup displays current key ID and rotation timestamp. |

## Recommended Checks

### Survey Submission Record Page

| Item | Details |
| --- | --- |
| **What it checks** | Whether the packaged `Survey_Submission__c` Lightning Record Page is activated. |
| **Why it matters** | Without activation, users see default layout instead of AutoSurvey submission experience. |
| **How to fix** | Click **Open Lightning Record Pages**, locate the AutoSurvey page, and activate as needed. |

### Publishing Health

| Item | Details |
| --- | --- |
| **What it checks** | The last 7 days of publishing activity: reporting-field setup steps that failed during survey publishes (the `Metadata_Deploy_Request__c` deploy transport) and survey responses that failed to write back to their reporting fields. |
| **Why it matters** | A publish whose reporting setup failed, or a response that never copied into reporting fields, leaves reports and exports incomplete even though responses themselves are captured safely. |
| **How to fix** | On failure, the check lists each affected survey or response with its error text. For failed reporting-setup steps, use the [reporting drift repair](#reporting-drift-repair) further down the page — the **Go to reporting repair** button jumps straight to it. For failed write-backs, open that survey in Survey Suites and click **Retry** on the **Reporting copy incomplete** card at the top of the page. |
| **Status values** | **Pass** = no failed publishes or write-backs in the last 7 days. **Fail** = failures found; each is listed. **Not Tested** = responses are still pending write-back — usually resolves within a few minutes. |

### Raw Response Access

Raw-response reports and CSV/ZIP exports show **individual** survey responses. Aggregate Insights apply
disclosure floors so small groups can't be re-identified; individual responses have no such floor, so
they are gated to authorized **raw-response administrators** only.

| Item | Details |
| --- | --- |
| **What it checks** | Whether the raw-response report folder is shared with the right users and the raw-response permission set is assigned. |
| **Why it matters** | Reveals individual, potentially identifying responses. Access is deliberately narrow so raw exports don't leak past the people entitled to see them. |
| **How to fix** | This is an **instructional** check, not a one-click repair — the **folder share and the permission set only work together**, and neither is safe to change automatically. Share the raw-response report folder with your raw-response administrators, then assign them the raw-response permission set. |
| **Status values** | **Not Tested** is expected here — the card is guidance, not an automated verification. |

<Warning>
Raw-response access exposes individual answers. Grant it only to users who are entitled to see
identifying data, and prefer aggregate Insights (which enforce disclosure floors) for everyone else.
</Warning>

### Survey Reports Access

The packaged **"AutoSurvey Survey Reports"** folder holds the aggregate/summary reports meant for
**every internal user**. Its metadata ships as `PublicInternal`, but Salesforce **ignores packaged
report-folder shares at install**, so the folder lands **hidden** until an admin shares it once.

| Item | Details |
| --- | --- |
| **What it checks** | Whether the packaged **AutoSurvey Survey Reports** folder is shared with internal users. |
| **Why it matters** | Without the share, the summary reports are invisible even though they're intended for the whole org — a packaging quirk, not a permissions decision you made. |
| **How to fix** | Click **Share the Survey Reports folder**. The one-click action grants internal-user access; the button disappears once the folder is shared. |
| **Status values** | **Pass** = folder shared with internal users. **Not Tested** / **Fail** = still hidden — click the share button. |

## Reporting Drift Repair

The **Check every live survey for reporting drift** card scans all live surveys for reporting setup that did not finish — missing reporting fields or missing field access. Responses are always captured safely even when reporting drifts; drift only affects reports and exports. This is the remedy [Publishing Health](#publishing-health) points at when reporting-setup steps fail.

Click **Scan** to list any drifted surveys, each with a one-line summary. **Review & repair** opens the same disclosure used by the publish flow: you see exactly which fields and permissions will change before the repair re-runs reporting setup for that survey.

## Public Survey Access

Enable this option if surveys should run for unauthenticated respondents via Experience Cloud.

### Experience Cloud Site Setup

To support guest respondents:

1. Create/activate an Experience Cloud site (**Digital Experiences -> All Sites** or **Setup -> Sites**).
2. Assign `AutoSurvey_Guest_Access` to the site guest user.
3. Deploy a survey flow and publish an Experience page containing the flow.

### Your Experience Sites

Setup automatically detects sites and readiness:
- **Ready**: Guest user has required access.
- **Not configured**: Guest user still missing required access.
- **Active survey flows**: Count of active AutoSurvey flows in org.

### CAPTCHA Configuration

AutoSurvey uses **Google reCAPTCHA v2** ("I'm not a robot") for bot protection on public surveys.

#### Set up CAPTCHA

1. Open [Google reCAPTCHA admin console](https://www.google.com/recaptcha/admin/create).
2. Create a key using **reCAPTCHA v2 -> I'm not a robot Checkbox**.
3. Add your Experience Cloud domain.
4. Paste Site Key and Secret Key into Setup Home.

#### CAPTCHA status indicators

| Status | Meaning |
| --- | --- |
| **Keys not configured** | No keys saved; no CAPTCHA protection active. |
| **Keys configured, hostname not set** | CAPTCHA works, but hostname verification not enforced. |
| **Keys configured and hostname set** | Full configuration with hostname verification. |

#### Secret key verification

When keys are saved, AutoSurvey verifies Secret Key with Google:
- **Secret key verified**: Key accepted.
- **Secret key rejected**: Invalid key.

#### Expected hostname (optional)

Set hostname to your Experience Cloud domain to enforce origin validation.

> Note: Required CSP and Remote Site entries for reCAPTCHA are package-provided.

### Default Favicon

Sets the org-wide default browser-tab icon for public survey links. Each survey resolves its favicon in three tiers: the survey's own favicon setting, then this org default, then the built-in AutoSurvey icon — so the org default applies to every survey that has not set its own.

Enter a public http(s) URL or a root-relative `/path` (up to 255 characters) and click **Save Favicon URL**. Leave blank to use the AutoSurvey default icon.

## Respondent Confidentiality Note

An org-wide confidentiality policy controlling whether surveys open with a soft confidentiality reassurance on their Welcome message (for example, "Your responses are confidential and will be used only to help us improve.").

| Policy | Effect |
| --- | --- |
| **Off** (default) | No confidentiality note is added. New surveys start with a blank welcome unless the author writes one. |
| **On by default** (`OnByDefault`) | The note is seeded onto each new survey's Welcome message. Authors can reword or remove it per survey. |
| **Required** | The note is seeded **and enforced**: every survey always shows the confidentiality note on its welcome screen, even if an author clears or replaces the welcome. |

The wording is an editable org-wide default (up to 255 characters); leave it blank to use the built-in text. The note is a soft reassurance respondents see once — it is not a legal guarantee and not a substitute for a Consent question.

## Sandbox Considerations

After sandbox refresh:

1. Post-install automation does not re-run.
2. Internal connection usually needs repair.
3. Control plane bootstrap may need to be re-run.
4. Connection verification should be run again.

Setup shows a sandbox reminder banner in sandbox environments.

## Troubleshooting

### "Page not found" for Digital Experiences

Register Salesforce Sites domain first in **Setup -> Sites and Domains -> Sites**, then create Experience site.

### Setup checks show UNKNOWN

Open details, retry repair, and use **Copy Diagnostic Info** for support.

### Internal connection fails after sandbox refresh

Expected behavior due to org domain URL changes. Run **Repair Internal Connection**.

### CAPTCHA says hostname missing

Refresh the page after saving keys. Status should update from persisted config.

### Control plane connection fails

Confirm outbound HTTPS callouts are allowed and verify `AutoSurvey_Control_Plane` Named Credential.
