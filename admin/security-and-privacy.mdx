# Security & Privacy

AutoSurvey is designed so you can run public-facing surveys on Salesforce without exposing broad guest access to your data model.

A public page can become risky when access controls drift over time. AutoSurvey's default architecture reduces that risk by separating public survey execution from internal admin and reporting paths.

## Secure-by-default approach

### 1) Token-gated public sessions (no record IDs in URLs)

- Public sessions use unguessable tokens.
- Tokens are validated server-side.
- The browser is not given "swap-able" record IDs that can be used to access someone else's data.

### 2) Public survey runtime with least privilege

- Public respondents do not need broad CRUD access to runtime objects.
- Survey writes happen through controlled server-side operations.
- Admin and setup actions are gated by explicit custom permissions.

### 3) Reporting access stays separate from public runtime

Reporting is handled through read-only permission sets, not by opening runtime objects to unauthenticated users.

- Suite-scoped reporting permissions for a single suite
- Optional global read-only reporting permissions across suites
- Super-user/admin permissions scoped to AutoSurvey artifacts (not broad org-wide access)

### 4) Safe deployment patterns

- Metadata deployment is generated server-side from known, allowlisted inputs.
- Deploy/setup capabilities are restricted to users with explicit deploy permissions.
- AutoSurvey avoids client-side "upload arbitrary metadata ZIP" deployment patterns.

### 5) Secret handling and logging hygiene

- API keys and secrets are stored using Salesforce-recommended patterns (for example Named Credentials / External Credentials).
- In **Bring your own key** mode, an admin enters each OpenAI or Anthropic key in the **AI provider** section on Setup Home. The key is saved, encrypted, in an External Credential in your org. It is not written to any record field and is not shown again.
- Secrets are never returned to the browser.
- Logging is sanitized to avoid exposing sensitive values.

### 6) Limits on public survey starts

- Each public survey accepts a limited number of anonymous starts per hour (200 by default). One browser that starts the same survey again and again is refused sooner (10 starts per hour by default), while the survey stays open to everyone else.
- A refused respondent reads that the refusal is temporary and about how many minutes to wait.
- When anonymous starts reach 80% of the hourly limit, and again when the limit is hit, the survey owner and the AutoSurvey admins get a Salesforce notification (bell) and an email. A respondent refused at the limit reads that the owner has been told.
- Setup Home shows a **Guest Start Cap** check when a survey hit its limit in the last 24 hours.
- A survey's CAPTCHA mode is **Auto** (the default), **Always** or **Never**. **Auto** shows a reCAPTCHA challenge to anonymous respondents only when the survey gets a sudden burst of starts. Without reCAPTCHA keys, **Auto** never challenges, and the hourly limit protects the survey. While a public link is active on a survey whose mode is not **Never**, Setup Home has a required **CAPTCHA Keys** check.

### 7) What a support request sends

The **What we'll send** preview in the support panel shows the exact text that **Send to AutoSurvey** sends and **Copy diagnostics** copies. It has no field for survey questions, responses, API keys or secrets. Some fields are free text (the text you type, setup check details and messages), so read them before you send.

## Designed for AppExchange-grade controls

AutoSurvey's architecture is intentionally designed to reduce common classes of security risk, including:

- Record access bypass patterns (for example IDOR)
- CRUD/FLS bypass patterns
- Overbroad permission assignments
- Secret exposure risks
- Unauthenticated admin/setup endpoints

## Practical customer benefits

- Faster go-live for public surveys
- Lower chance of accidental data exposure via guest configuration
- Clear role-based permissioning for admins, deployers, and analysts
- Easier audit and security review conversations

## What AutoSurvey does not claim

- It cannot prevent every org-level misconfiguration outside the product.
- It does not replace customer governance, compliance, or security policy.
- It reduces common exposure paths by default and provides clearer security boundaries.

## Recommended secure setup checklist

- Keep runtime/public access minimal.
- Use read-only reporting permission sets for analysts.
- Restrict deploy/setup permissions to a small admin group.
- Do not expose sensitive token fields in reports or list views.
- Use supported credential patterns (BYOK/Named Credential where applicable), not ad-hoc key storage.

## Privacy controls you can set

The sections above describe the architecture. These are the controls **you** operate. A privacy
review usually asks for this list.

### Whether a respondent is identified

Each survey sets **Identify the respondent** to `Off`, `Optional` or `Required`, on the **Answers** card of its **Settings** tab.

| Value | What the respondent sees | What you get |
| --- | --- | --- |
| `Off` | Nothing. They answer and finish | No responder identity captured |
| `Optional` | A step **after** they finish | Unlinked by default — a results subscription, not a link to their answers. The respondent may opt into linking on that step |
| `Required` | A registration step **before** question 1 | Their answers are linked to them |

`Optional` is the setting to use when you want to stay in touch without tying a person to their
answers. The default is not to identify anyone. `Optional` and `Required` promise the person a
results report, so the survey needs a scheduled close date or a report cadence (on the Send tab)
before you can turn them on.

**Anonymous responses.** `Off` captures no responder name, no email and no record link. AutoSurvey
still stores a session key on the response so a part-finished survey can be resumed. A resume also
needs a separate secret that only the respondent's browser holds. That key
identifies a session, not a person, and nothing joins it to a Contact, Lead or User unless you
switch identification on.

### The confidentiality note

Setup Home carries an **org-wide** **Confidentiality note policy**, in the **Respondent
Confidentiality Note** section, with three values:

| Value | Effect |
| --- | --- |
| **Off** | No confidentiality note (the default) |
| **On by default** | New surveys are seeded with the note on their Welcome message. An author may edit or remove it |
| **Required** | **Every** survey always shows the note. Authors cannot remove it |

**Required** is the setting for an org that must make the same promise on every survey. You can edit
the wording of the default note in the same place.

### Masking an answer

Give a question the **`Masked Text`** display type and its answer is stored masked. Reading an
unmasked answer needs the **Reveal Masked Answers** custom permission, so masking is a permission
boundary and not only a display choice. Assign that permission to the small group who genuinely
need the raw value.

### Disclosure floors and retention ceilings

Two custom metadata types let you make AutoSurvey's own defaults **stricter**, and only stricter:

| Setting | What it governs | Which direction you may move it |
| --- | --- | --- |
| `Survey_Disclosure_Policy__mdt` | The minimums that gate what any respondent-facing surface may disclose — minimum n, minimum cell, sensitive minimum n, margin floor | **More conservative only.** An override cannot lower a floor |
| `Survey_Retention_Policy__mdt` | How long a respondent registration is kept before it is purged | **Shorter only.** An override cannot extend retention |

The clamps run one way on purpose. A floor you could lower is not a floor, and a retention ceiling
you could raise would defeat the purge.

## Your data &amp; the law (data governance)

AutoSurvey is a business-to-business tool. For survey-respondent personal data, **you (the
subscriber) are the data controller** and **Mindshare Studio LLC is a processor** acting on your
instructions. The legal pack below states our commitments in full.

### Where your data lives

- **Survey responses stay in your own Salesforce org.** They are stored in AutoSurvey's managed
  objects (and an optional customer-owned reporting object, which each survey can turn off). Responses are **not** sent to
  Mindshare Studio, are **not** stored on the AutoSurvey server, and are **not** sent to any AI service.
- **Survey design content** (the questions you author, whether via AI generation in Salesforce or
  the Google Sheets add-on) is processed in your org and, where the Sheets add-on is used, hosted in
  our managed Google Workspace.
- **Account, licensing, and AI-usage metadata** is held in our hosted AutoSurvey server (org ID,
  domain, plan, hosted AI keys, token/spend telemetry). A key you bring yourself (BYOK) stays in
  your org.

### AI features

The optional AI features (question generation) send only the **survey
design content you author** to an AI provider (OpenAI or Anthropic, depending on the model selected)
— never respondent answers. Analytics ("Insights") and export run inside your org with no AI. In
**BYOK** mode, AI calls go directly from your org to your provider; in **hosted** mode AutoSurvey
uses our managed key and meters token usage through the AutoSurvey server.

### Sub-processors

Salesforce, Inc. (control-plane hosting), Google LLC (Sheets/Drive hosting), OpenAI, L.L.C. and
Anthropic, PBC (AI authoring). See the DPA for the maintained list.

### On uninstall

Uninstalling the managed package removes AutoSurvey's managed response objects and their data per
Salesforce's standard behavior. A **customer-owned mapped reporting object and its data remain**,
and that object is built to stay readable once the managed parent is gone.

Alongside one field per question, AutoSurvey stamps **18 stored fields** onto every row of that
object. They are stored values, not formulas, so they survive the uninstall:

- **Which survey** — suite name and code, form name and code, release label, release number,
  import version.
- **When, and what state** — status, started at, submitted at, last saved at, session key.
- **Who answered** — responder name and email as frozen text, plus Contact, Lead and User lookups.
  The text copies stay readable even if the Contact is later deleted.
- **Every answer** — `Survey Answers (JSON)`, the complete answer set as one payload, up to 32 KB.
  It keeps multi-select and matrix answers that the per-question columns flatten.

A stamp is skipped only where one of your own questions already claims that field name.

So reporting on the mapped object keeps working after uninstall. **Export any responses you want to
keep before uninstalling** — that is still the safe order, and it is the only way to keep the
in-package detail records.
