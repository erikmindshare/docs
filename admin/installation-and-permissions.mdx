title: "Installation & Permissions"
description: "What to assign to admins, to staff answering surveys, to community members, and to the guest user behind a public link."
---


AutoSurvey ships **two permission set groups** and a set of individual permission sets. Almost
everyone should get a group.

## Start here: the two groups

| Assign this | To | What they get |
| --- | --- | --- |
| **AutoSurvey Full Admin** | Anyone who builds, publishes or configures surveys | Everything: the app, the data model, publishing, deploys, and full field access |
| **AutoSurvey Respondent** | Internal staff who *answer* surveys | The **My Surveys** inbox and the survey runner |

<Warning>
  **Assign the groups, not the sets inside them.** The Respondent group exists because its two
  members are useless apart: with **My Surveys** alone, the inbox lists a survey and shows a
  **Take survey** button that cannot open it. The Full Admin group's description says the same
  thing — assign it instead of the seven admin sets individually.
</Warning>

## Respondents outside your staff

| Who they are | Assign |
| --- | --- |
| **Community / portal members** signed in to your Experience site | **Member Runtime** — read-only runtime plus My Surveys |
| **Anyone with the link**, no login | **AutoSurvey Guest Access** — assign to the site's **guest user**, not to a person |

<Note>
  Guest access is a property of the Experience site, not of an individual. If a public survey isn't
  working for respondents, the guest user's permissions are the first thing to check — and the
  **Public Link Setup** card on Publish & Share checks it for you.
</Note>

## Narrower roles

Reach for these when Full Admin is more than someone needs:

| Permission set | Grants |
| --- | --- |
| **Super User** | Configuration, runtime data and deployment workflows, including **View All Records** on the AutoSurvey objects and **Modify All Records** on survey assignments — but not the org-wide View All Data or Modify All Data permissions |
| **AutoSurvey Raw Response Access** | Individual, unaggregated response data and the restricted raw-response reports. Grant deliberately |
| **Global Reporting** | Read-only access to the reporting objects. Generated by AutoSurvey — don't hand-edit it |
| **AutoSurvey List View Access** | Lets someone create their own private list views on objects they can already see |

## Connections you only need if you use them

Each of these unlocks one connection and does nothing otherwise:

| Permission set | Needed for |
| --- | --- |
| **OpenAI BYOK Access** / **Anthropic BYOK Access** | Using your own AI provider key |
| **GetFeedback API Access** | Importing from a private GetFeedback account |
| **SurveyMonkey API Access** | Importing from a private SurveyMonkey account |
| **Self Org Access** | The **Self Org** external credential, used when AutoSurvey routes callouts back into your own org |

## Delegating single actions

Some actions are gated by their own **custom permission**, so you can grant one without granting the
role around it:

| Custom permission | Lets someone |
| --- | --- |
| **Publish Survey** | Take a release live |
| **Close Survey** / **Pause Collection** / **Retire Survey** | Change a survey's lifecycle state |
| **Send Invitations** / **Assign Recipients** | Send a survey out and choose who gets it |
| **Reminders Live** | Let reminder schedules actually send |
| **Delete Submission** | Delete a response |
| **Reveal Masked Answers** | See the contents of a masked answer |
| **Mark Data Quality** | Flag a response's data quality |
| **AutoSurvey: Raw Response Access** | Read individual response data |
| **Deploy Surveys** | Run metadata deploy operations |

<Tip>
  These are how you give someone exactly one capability — a coordinator who may send invitations but
  not publish, or an analyst who may read raw responses but not delete them.
</Tip>

## The sets you should leave alone

Several permission sets exist as building blocks and aren't meant to be assigned directly:

* The seven inside **AutoSurvey Full Admin**, and the two inside **AutoSurvey Respondent** — assign
  the group.
* **Setup Bootstrap**, a minimal set for whoever runs first-time setup: the setup-gating permission,
  plus just what Setup Home needs before the full admin sets are assigned — the app and its tabs,
  Apex access for the setup pages, the control-plane connection, and two Suite fields.
* **AutoSurvey Flat Object Access**, which intentionally contains no permissions in the core package.
* **AutoSurvey SuiteKey Reporting TEMPLATE**, which is a pattern to copy per suite, not a set to
  assign.

<Note>
  AutoSurvey is a managed package, so its API names carry the `atsv__` namespace prefix in Setup —
  `atsv__AutoSurvey_Admin`, `atsv__Suite__c`. Labels don't show it; searches sometimes need it.
</Note>
